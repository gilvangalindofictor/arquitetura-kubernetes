# ADR-074: Namespace Migration to Deterministic Naming Pattern

**Status:** PROPOSED
**Date:** 2026-02-24
**Deciders:** Platform Team
**Technical Story:** GAP-009 Kyverno Governance Policies Require Deterministic Namespace Naming

---

## Context

The EKS staging cluster currently has **18 namespaces** (excluding Kubernetes system namespaces). An analysis revealed that **17 of 18 namespaces (94%)** do not conform to the governance naming pattern required by GAP-009 Kyverno policies.

### Current State

**Namespace Naming Issues:**
1. **Inconsistent suffixes:** `-system`, `-staging`, or no suffix
2. **No environment prefix:** Cannot distinguish staging vs production by namespace alone
3. **No domain classification:** Platform, data, security, observability not distinguished
4. **Legacy naming:** Inherited from Helm chart defaults (e.g., `harbor-system`, `vault-system`)

**Examples of Non-Conformance:**
```
✗ harbor-system       (should be: staging-platform-harbor)
✗ vault-system        (should be: staging-security-vault)
✗ monitoring          (should be: staging-observability-monitoring)
✗ data-services       (should be: staging-data-infrastructure)
✗ gitlab-staging      (should be: staging-platform-gitlab)
```

**Only 1 Compliant Namespace:**
```
✓ staging-integration-test
```

### GAP-009 Kyverno Governance Policy

**Required Pattern:**
```
{env}-{domain}-{product}
```

**Components:**
- `env`: Environment identifier (staging, production, dev)
- `domain`: Service domain (platform, data, observability, security, governance)
- `product`: Product/service name (argocd, gitlab, harbor, postgresql, etc.)

**Policy Enforcement:**
- ClusterPolicy validates namespace creation
- Admission webhook blocks non-conformant namespace names
- Policy mode: `enforce` (not `audit`)

**Examples:**
```
staging-platform-argocd
production-data-postgresql
dev-security-vault
```

### Why Migration is Required

**1. Governance Compliance**
- Kyverno policies cannot enforce naming without breaking existing namespaces
- Current state: Policy in `audit` mode (no enforcement)
- Target state: Policy in `enforce` mode (100% compliance)

**2. Operational Clarity**
- Engineers cannot identify environment from namespace name alone
- `monitoring` could be staging or production (ambiguous)
- Cross-cluster operations require constant context switching

**3. Multi-Cluster Scaling**
- Future production cluster requires distinct namespace names
- Namespace name collisions if promoting staging → production
- Example: `harbor-system` in both clusters → which is production?

**4. Cost Allocation (FinOps)**
- Namespace labels track costs by environment/domain/product
- Current naming inconsistent with label structure:
  - Namespace: `harbor-system`
  - Labels: `Environment=staging`, `domain=platform`, `product=harbor`
  - Name does not reflect labels → confusion in cost reports

**5. Disaster Recovery**
- Backup/restore scripts use namespace names as identifiers
- Non-deterministic names complicate automation
- Example: Restore `harbor-system` → which cluster? staging or production?

---

## Decision

**Migrate all 17 non-conformant namespaces to deterministic naming pattern over 5 waves (7 working days).**

### Domain Classification

**5 Domains:**
1. **platform (7):** Core services consumed by developers (ArgoCD, GitLab, Harbor, Keycloak, SonarQube, ArgoCD Test)
2. **data (3):** Data layer services (Infrastructure, RabbitMQ Operator, Redis Operator)
3. **observability (2):** Monitoring + tracing (Monitoring stack, OpenTelemetry Test)
4. **security (3):** Security infrastructure (Cert-Manager, External Secrets, Vault)
5. **governance (2):** Policy enforcement (Kyverno, Test)

### Migration Strategy

**4 Migration Patterns:**

**Pattern A (Stateless):** 7 namespaces
- cert-manager, external-secrets-system, kyverno, redis-operator, argocd-test, otel-test, test-governance
- No PVCs, quick migration (<10min downtime)
- Rollback: Delete new namespace

**Pattern B (External RDS):** 2 namespaces
- argocd, keycloak
- Stateless pods, all data in external PostgreSQL RDS
- Migration: RDS connection switch only
- Rollback: Delete new namespace, point back to RDS

**Pattern C (StatefulSets + PVCs):** 5 namespaces
- gitlab-staging (50GB), harbor-system (6GB), monitoring (94GB), sonarqube (20GB), vault-system (15GB)
- High risk: VolumeSnapshots required
- Migration: Snapshot → restore → validate data integrity
- Rollback: Delete new namespace, old namespace + snapshots remain

**Pattern D (Operator-Managed CRDs):** 2 namespaces
- data-services (Redis, RabbitMQ CRs), rabbitmq-system (operator)
- Operator watches all namespaces (cluster-scoped)
- Migration: Recreate CRs in new namespace, operator reconciles
- Rollback: Delete new namespace, recreate CRs in old namespace

### Execution Plan (5 Waves)

**Wave 1 (2026-02-25):** Foundation Layer - 6 namespaces (3h parallelized)
- cert-manager, external-secrets-system, redis-operator, test-governance, otel-test, argocd-test
- Pattern A (stateless)
- Risk: LOW

**Wave 2 (2026-02-25):** Operators - 2 namespaces (3h sequential)
- rabbitmq-system, kyverno
- Pattern A + D
- Risk: MEDIUM

**Wave 3 (2026-02-26):** Security + Data - 2 namespaces (7h sequential)
- vault-system, data-services
- Pattern C + D
- Risk: HIGH (Vault = critical path for ESO)

**Wave 4 (2026-02-27):** Platform Core - 3 namespaces (7h sequential)
- keycloak, argocd, sonarqube
- Pattern B + C
- Risk: MEDIUM (Keycloak = SSO for all services)

**Wave 5 (2026-02-28):** Platform Services - 2 namespaces (9h sequential)
- harbor-system, monitoring
- Pattern C
- Risk: HIGH (large PVCs: 6GB + 94GB)

**Wave 6 (2026-02-28):** GitLab CRITICAL - 1 namespace (4h dedicated)
- gitlab-staging
- Pattern C
- Risk: CRITICAL (50GB PVC, source code repositories)

**Total Time:** 35h execution + validation buffer = **40h (7 working days)**

### Rollback Strategy

**Retention Periods:**
- Standard: 7 days (LOW/MEDIUM risk)
- Extended: 14 days (HIGH/CRITICAL risk: GitLab, Vault, Harbor, Monitoring)

**Rollback Procedure:**
1. Delete new namespace: `kubectl delete namespace <new-ns>`
2. Old namespace remains operational (no impact)
3. VolumeSnapshots preserved for disaster recovery
4. RDS databases unchanged (no data migration)

**Rollback Triggers:**
- CrashLoopBackOff pods (>5min)
- Data integrity validation fails
- Ingress 502/503 (>30min)
- ExternalSecrets fail to sync (Vault connection)

## Consequences

### Positive

**1. Governance Compliance**
- 100% namespaces conform to GAP-009 Kyverno policy
- Enable policy `enforce` mode (currently `audit` only)
- Prevent future non-conformant namespaces

**2. Operational Clarity**
- Environment visible in namespace name (staging-*)
- Domain classification clear (platform, data, security, etc.)
- Multi-cluster operations simplified (no name collisions)

**3. Cost Allocation**
- Namespace names align with FinOps labels
- Cost reports easier to interpret
- Example: `staging-platform-harbor` → "Staging Platform Harbor costs"

**4. Automation & IaC**
- Terraform resources can use deterministic naming
- Backup/restore scripts simplified
- GitOps patterns more consistent

**5. Multi-Cluster Readiness**
- Production cluster can use `production-*` prefix
- Clear distinction: `staging-platform-gitlab` vs `production-platform-gitlab`
- Namespace federation simplified

### Negative

**1. Migration Effort**
- 40 hours execution time (7 working days)
- 4 engineers required (parallel execution)
- Downtime: 9h total across all namespaces (staging = acceptable)

**2. Downtime Impact**
- GitLab: 2h (blocks CI/CD pipelines)
- Keycloak: 0.5h (all SSO logins fail)
- Monitoring: 1.5h (blind operations)
- Others: 5h cumulative
- **Total:** 9h downtime (staged over 7 days)

**3. Risk of Data Loss**
- GitLab: 50GB PVC (source code repositories) - CRITICAL
- Vault: 15GB PVC (encrypted secrets) - HIGH
- Harbor: 6GB PVC (OCI image blobs) - HIGH
- Monitoring: 94GB PVCs (metrics/logs) - MEDIUM (rebuildable)
- Mitigation: VolumeSnapshots + 14d retention + double backups

**4. Documentation Debt**
- Update 50+ runbooks with new namespace names
- Update Terraform modules
- Update Grafana dashboards
- Update Slack alerts
- Update disaster recovery procedures

**5. Team Training**
- Engineers must learn new naming pattern
- Muscle memory: `kubectl get pods -n harbor-system` → `kubectl get pods -n staging-platform-harbor`
- Alias/shortcuts need updates

## Alternatives Considered

### Alternative 1: Keep Legacy Names, Enforce for New Namespaces Only

**Description:** Grandfather existing namespaces, only enforce pattern for new namespaces.

**Pros:**
- Zero migration effort
- No downtime risk
- Immediate policy enforcement for new resources

**Cons:**
- 94% namespaces remain non-conformant (17/18)
- Inconsistent naming forever (technical debt)
- Multi-cluster collisions persist
- Cost allocation remains confusing

**Decision:** REJECTED (does not solve core problem)

---

### Alternative 2: Namespace Aliasing (Labels Only)

**Description:** Keep legacy names, add labels for governance:
```yaml
metadata:
  name: harbor-system
  labels:
    governance.k8s.io/name: staging-platform-harbor
```

**Pros:**
- Zero migration effort
- No downtime
- Kyverno can validate labels instead of names

**Cons:**
- Namespace name still non-deterministic
- Labels can be removed (not immutable like names)
- CLI operations still use legacy names (`kubectl get pods -n harbor-system`)
- Cost reports still confusing

**Decision:** REJECTED (does not improve operational clarity)

---

### Alternative 3: Blue/Green Migration (Parallel Namespaces)

**Description:** Run old + new namespaces in parallel, gradual traffic cutover.

**Example:**
- Deploy `staging-platform-harbor` (new)
- Keep `harbor-system` (old)
- Route 10% traffic → new, 90% → old
- Gradually increase to 100% → new
- Delete old after validation

**Pros:**
- Zero downtime (canary migration)
- Instant rollback (traffic switch)
- Validate new namespace under production load

**Cons:**
- Double resource cost during migration (2× pods, 2× PVCs)
- Complex traffic routing (requires service mesh or weighted ingress)
- PVC data sync required (rsync, storage replication)
- 2-4× migration time (parallel operation + validation)

**Decision:** REJECTED (cost + complexity outweigh benefits for staging)

---

### Alternative 4: In-Place Namespace Rename

**Description:** Rename namespace using Kubernetes API:
```bash
kubectl patch namespace harbor-system -p '{"metadata":{"name":"staging-platform-harbor"}}'
```

**Pros:**
- No data migration
- Zero downtime (theoretically)
- Simple operation

**Cons:**
- **Kubernetes does NOT support namespace rename** (metadata.name is immutable)
- Would require:
  1. Export all resources
  2. Delete namespace
  3. Recreate with new name
  4. Re-apply resources
  - This is equivalent to our Pattern C migration (not simpler)

**Decision:** REJECTED (not technically feasible)
